# 事例紹介：既存の予約システムに、安全に AI を組み込む

コワーキングスペースの予約・会員管理サービス「ee-office」（Rails API ＋ Next.js、AWS で本番運用中）に、あとから AI 機能を3つ組み込んだ記録です。
「現場の課題を聞く → 既存の API を AI の道具にする → 安全に本番で使える形にする → 効果を数字で示す」を、1つの機能ずつ通しました。

> デモ：[docs/ai/demo/](demo/README.md)（予約・分析・FAQ の操作の録画）

## 1. 結果の要約

| 機能 | 使う人 | 何ができるか | 評価（実際の Claude） | 1回の料金 | 応答（中央値） |
|---|---|---|---|---|---|
| 話して予約できるアシスタント | 会員 | 「明日の午後、渋谷で4人・2時間」から空きを調べ、候補を出す。予約は会員がボタンで確定 | **20/20** | 約2.1円 | 6.5秒 |
| 売上・利用状況の分析アシスタント | 運営者 | 「先月は何曜日の予約が多かった？」に、集計の API だけを使って答える | **16/16**・確かめられない数字 0 | 約1.8円 | 4.9秒 |
| ご利用ルールの FAQ ボット | 会員 | ルールを検索し、答えの文に根拠を引用して返す（RAG） | **16/16**・引用 9/9 | 約1.5円 | 4.0秒 |

- 3つとも本番（https://ee-office.matsushin.tech ）に出している。AI まわりのコードは約3,800行（うちテスト・評価が約1,650行。生成物を除く）、PR は6本（#59〜#64）
- 既存の業務ロジック（Rails のモデル・権限・料金計算）は一行も AI 向けに書き換えていない。AI は既存の API の「使い手」として後から入った

## 2. 前提：既存のシステム

- Rails 8 の API（認証・Pundit の権限・予約の二重登録防止・料金計算）と Next.js 16 の画面。API の仕様書（OpenAPI）はテストから生成している
- 本番は AWS（ECS Fargate・RDS・Terraform）。エラーは Sentry、通知は Slack

このシステムを「顧客の既存システム」に見立てて、**中身を作り直さずに AI を足す**ことを条件にした。

## 3. 課題から始める

機能ごとに、作る前に課題メモを書いた（[01](01_課題メモ.md)・[03](03_課題メモ_分析アシスタント.md)・[04](04_課題メモ_FAQボット.md)）。

| 機能 | 困りごと（仮説） | 成功の基準（作る前に決めた） |
|---|---|---|
| 予約 | 条件は頭にあるのに、画面では拠点 → 日付 → 時間帯を1つずつ選ぶ。拠点をまたいだ比較が手間 | 正答 90% 以上・AI による予約 0件・中央値 10秒以内・1回 10円以内 |
| 分析 | 見たい切り口（曜日・時間帯・稼働率）が画面にない。手で集計すると数え方がぶれる | 正答 90% 以上・確かめられない数字 0・中央値 20秒以内・1回 15円以内 |
| FAQ | ルールが画面ごとに散らばっている。AI が答えるなら、根拠が分からないと信用できない | 正答 90% 以上・正しい引用 100%・中央値 10秒以内・1回 5円以内 |

3つとも、決めた基準をすべて満たした。

## 4. しくみ

```
画面（Next.js）── Server Action（ログイン・権限・入力の検証）
                    │
                    ▼
              runAiFeature（共通の入り口）
                ├ Rails に相談の開始を記録（会員ごとの1日の回数の上限）
                ├ Claude（Opus 5.5）を tool runner で呼ぶ
                │    道具＝OpenAPI の仕様書から作った「許可リストの GET だけ」
                │    道具は利用者本人のトークンで既存の API を呼ぶ（権限は Pundit がそのまま決める）
                ├ プロンプトキャッシュ（指示・道具の定義）
                └ 結果にかかわらず、トークン数・料金・応答時間を Rails に記録（文章は残さない）
                    │
                    ▼
              機能ごとの「確かめる」処理 ─▶ 画面
                予約：候補をコードで確かめる／分析：数字を集計の結果と照らし合わせる／FAQ：引用をルールの項目に結ぶ
```

### 道具は仕様書から自動で作り、渡すものは人が決める

- `allowlist.json`（機能ごとの許可リスト）に書いた操作だけを、OpenAPI の仕様書から AI の道具に変換する（`gen-ai-tools.mjs`）。**GET 以外を書くと生成が失敗する**
- 何を渡し、何を渡さないかの理由は [02_AIに渡す操作.md](02_AIに渡す操作.md) に表で残す（例：`/api/me` はメールアドレスを含むので予約には渡さない、会員一覧は分析にも渡さない）
- 道具の引数は仕様書の型（整数・日付・列挙・形）で確かめてからパスに埋める。`../admin` のような書き換えは通らない

## 5. 安全の設計

| 原則 | 具体的に |
|---|---|
| AI に確定させない | 予約・取り消し・プランの変更は人がボタンで行う。AI の道具は読み取りだけ |
| AI に特別な権限を持たせない | 道具は利用者本人のトークンで既存の API を呼ぶ。分析は管理者だけ（画面・Server Action・Rails の Policy の三重） |
| 計算は既存のコードに任せる | 料金・空き・営業時間・集計の数え方は Rails。AI に SQL を書かせない、金額を計算させない |
| AI の答えをそのまま出さない | 予約：AI は ID と時刻だけを返し、名前・料金は API の値で付ける。分析：数字を照らし合わせて ⚠ を付ける。FAQ：引用の場所は API が返し、ルールにない出典は捨てる |
| 失敗しても困らない | キーがない・上限に達した・AI が失敗したときは、通常の画面へ案内する |
| 記録は数字だけ | 入力の文章や AI の回答は保存しない。トークン数・料金・応答時間・道具の回数だけを残す |

機能ごとに「何で正しさを担保するか」を変えた。予約は**コードで確かめる**、分析は**数字の照らし合わせ**、FAQ は**引用**。FAQ だけ構造化出力を使っていないのは、引用（citations）と同時に使えない API の制約による。

## 6. 評価

- 評価データ（予約20件・分析16件・FAQ16件）を、実際の Claude と手元の Rails で流す仕組み（`npm run eval:*`）を作り、毎回の結果を `RESULTS.md` に1行ずつ残す
- 分析と FAQ の値の質問は、**正解を評価から同じ API を直接呼んで求める**。データが変わっても期待を書き直さなくてよい
- FAQ の検索だけの評価（18件）は Claude を呼ばないので、CI で毎回流す
- 正常な質問だけでなく、聞き返し・予約できない条件・データのない月・ルールに載っていないこと・他人の情報を求める指示・範囲外の質問を入れた

### 数字が下がったとき、まず評価の期待を疑った

予約アシスタントの1回目は 18/20 だった。外れた2件（営業時間外の依頼）は、AI が「営業は20時までなので、代わりに19時〜20時は？」と理由と代わりの候補を出していた。**AI の誤りではなく、評価データの期待（候補なし）が課題メモ（理由と代わりの案を返す）と食い違っていた**。仕様を決め直して評価を直し、理由を記録に残した（2回目 20/20）。プロンプトを先にいじっていたら、正しい振る舞いを壊していた。

### 検証の仕組みにも限界がある

分析アシスタントの数字の照らし合わせは、2つの値の差や比も認める。テストで「どこからも作れないはずの 99.9」が 400,000 ÷ 400,300 で当てはまった。組み合わせが多いと偶然一致する。照らし合わせは「ずれを見つける仕組み」であって正しさの証明ではない、と割り切り、正しさは評価で別に測ることにした。

## 7. 費用と運用

| 項目 | 内容 |
|---|---|
| 1回の料金 | 1.5〜2.1円（Opus 5.5。入力の約80〜88%をプロンプトキャッシュから読む） |
| 使いすぎの防止 | 利用者ごとに1日20回（Rails で行ロックして数える）、Console の月の上限額 |
| 鍵の管理 | 本番の API キーは SSM の SecureString からタスクに渡す。開発用と本番用のキーを分け、料金を分けて見られ、片方だけ止められる |
| 見える化 | 1回ごとのトークン数・料金・応答時間・道具の回数・失敗の理由（上限・タイムアウト・断られた）を記録 |
| 評価の費用 | 全件を1回流して 25〜40円 |

## 8. 本番への導入の手順

1. Rails：利用記録の表のマイグレーション（起動時に自動で適用）と、集計の API を追加
2. Terraform：`anthropic_api_key` を `terraform.tfvars` に書いて apply（SSM に保存し、タスク定義に渡す）
3. frontend・backend をデプロイ
4. 本番で1回ずつ動かして確かめる（予約・分析・FAQ）

キーを入れなければ AI 機能は出ず、通常の画面への案内だけが出るので、**コードとキーを別々に出せる**。

## 9. 学んだこと

1. **作る前に成功の基準を決める**。決めておくと、評価の数字が「良いか」を議論しなくて済み、期待の食い違いにも気づける
2. **AI に任せる範囲を、道具の許可リストで決める**。プロンプトで「〜しないで」と頼むより、できない形にする方が確実
3. **AI の答えは、何かと照らし合わせてから出す**。機能ごとに照らし合わせる相手（API の値・集計の結果・ルールの文書）を選ぶ
4. **評価は仕様の一部**。評価データも間違えるので、外れたらまず期待を疑う
5. **検証の仕組みにも限界を書いておく**。何を保証し、何を保証しないかを言葉にする

## 10. 次にやるなら

- 会話が続く相談（聞き返し → 答える）の評価。今は1往復のケースだけ
- 本番の利用記録から、断られた・失敗した相談を週ごとに見て、評価データに足す仕組み
- 文書が増えたときの FAQ の検索（埋め込みへの切り替え）と、その比較の評価
- 応答を少しずつ表示する（ストリーミング）で、待ち時間の体感を短くする
- 別の業務システムへの横展開：仕様書があれば、許可リストを書くだけで道具ができる
