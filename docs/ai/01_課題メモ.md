# 課題メモ：話して予約できるアシスタント

作る前に、だれが・何に・どれくらい困っているかと、成功の基準を決める。
**【要確認】** の印は、運営者（松田）の実際の経験で確かめて書き直すところ。

## 1. 使う人

| 人 | 状況 | 今のやり方 |
|---|---|---|
| 会員（フリーランス・会社員） | 打ち合わせ・オンライン会議の部屋を、移動の合間にスマホで探す | 拠点の一覧 → 拠点を選ぶ → 日付を選ぶ → 空きの表を見る → 予約 |
| 出張中の会員 | 知らない街で「駅の近くで、夕方に2時間」使える場所を探す | 都道府県で絞り込み → 拠点ごとに空きを見比べる |
| 拠点のスタッフ・運営者 | 「◯◯で空いてる会議室ある？」と電話やチャットで聞かれる | 管理画面で拠点ごとに空きを見て答える **【要確認】どれくらいの頻度か** |

## 2. 困りごと（仮説）

1. **条件から探せない**：「明日の午後・渋谷・4人・2時間」のような条件は頭の中にあるのに、画面では拠点 → 日付 → 時間帯の順に一つずつ選ぶ必要がある
2. **拠点をまたいだ比較が手間**：近くの拠点が満室のとき、ほかの拠点の空きを見るには画面を行き来する
3. **ルールが分かりにくい**：営業時間・30分単位・プランごとの月の上限で予約できない理由が、予約の直前まで分からない
4. **運営者への問い合わせ**：上の 1〜3 が、スタッフへの問い合わせになっている **【要確認】**

## 3. 作るもの（範囲）

- 会員が自然な文で条件を書くと、AI が拠点・スペース・空きを調べ、**予約の候補（拠点・スペース・開始と終了・料金の目安）を最大3件**出す
- 会員が候補を選び、**「この内容で予約」ボタンを押すと、既存の予約の処理（`POST /api/reservations`）で予約する**。AI は予約しない
- 条件が足りないとき（日付・場所が分からない）は、推測せずに聞き返す
- 予約できない条件（営業時間外・定員を超える）は、理由と代わりの案を返す

範囲外：予約の変更・キャンセル、ドロップイン（入退室）、支払い、管理者の操作

## 4. 成功の基準

| 指標 | 目標 | 測り方 |
|---|---|---|
| 候補の正しさ | 評価データで 90% 以上 | `frontend/evals/booking/cases.json` を流し、候補が条件（場所・人数・時間帯・営業時間・空き）を満たすかを自動で判定 |
| 安全 | AI による予約 0件、他人の予約の表示 0件 | 評価データの安全のケースと、道具が読み取りだけであることのテスト |
| 予約までの手数 | 画面の移動 4回以上 → 入力1回＋ボタン1回 | 画面の操作を数える |
| 応答時間 | 中央値 10秒以内 | 記録した応答時間 |
| 料金 | 1回の相談あたり 10円以内 | 記録したトークン数から計算 |
| 問い合わせ | スタッフへの「空いてる？」の問い合わせが減る | **【要確認】** 実際の拠点で測れるか |

## 5. リスクと対策

| リスク | 対策 |
|---|---|
| 入力に AI への指示を紛れ込ませる（プロンプトインジェクション） | AI の道具は読み取りだけ。予約は人のボタンで既存の処理を通す。評価データにケースを入れる |
| 他人の予約が見える | 道具は会員本人のトークンで API を呼ぶ。空き状況の API は他人の予約を「誰のものか」なしで返す（既存の仕様） |
| 料金の使いすぎ | 会員ごとに1日の回数の上限、Anthropic の Console で月の上限額、入力の長さの上限 |
| AI が止まる・間違える | 通常の画面へのリンクを常に出す。候補は予約の前に人が確かめる |
| 日時の取り違え（UTC と日本時間） | 今の日時（日本時間）を毎回渡す。候補の時刻は API の値をそのまま使う |
