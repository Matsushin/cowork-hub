# 課題メモ：ご利用ルールに答える FAQ ボット

作る前に、だれが・何に困っているかと、成功の基準を決める。
**【要確認】** の印は、運営者（松田）の実際の経験で確かめて書き直すところ。

## 1. 使う人と困りごと（仮説）

| 人 | 困りごと | 今のやり方 |
|---|---|---|
| 会員 | 「キャンセル料はかかる？」「チェックアウトを忘れたら？」「月額でもドロップインは有料？」など、ルールが分からない | スタッフに聞く・試してみてエラーで知る |
| 拠点のスタッフ | 同じ質問に何度も答える **【要確認】どれくらいの頻度か** | 口頭・チャットで答える |

1. ルールが画面ごとに散らばっていて、まとまった説明がない
2. 営業時間・料金は拠点ごと・プランごとに違うので、文書に書くと古くなる
3. AI が答えるなら、**何を根拠に答えたかが分からないと信用できない**

## 2. 作るもの（範囲）

- ご利用ルールを文書にまとめ（`docs/rules/`）、だれでも読める画面（`/rules`）に出す。この文書を FAQ ボットの元にする
- 会員が質問すると、AI がご利用ルールを検索し、**答えの文に根拠の項目を引用して**返す。引用は画面のルールの項目へのリンクになる
- 変わる値（営業時間・料金・プランの上限）は文書に書かず、拠点・プランの API から調べる
- ルールにないこと（支払い方法・設備など）は推測せず、スタッフへ案内する

範囲外：操作の代行（予約・取り消し・プランの変更）、会員ごとの情報（自分の予約・請求）、拠点の設備の案内

## 3. 成功の基準

| 指標 | 目標 | 測り方 |
|---|---|---|
| 答えの正しさ | 評価データで 90% 以上 | `frontend/evals/faq/cases.json`。ルールの質問は、正しい項目を引用し、要点の語があるか。値の質問は、API の値（評価から直接呼ぶ）が答えにあるか |
| 引用 | ルールの質問で、正しい項目を 100% 引用 | 同上（引用の正しさを別に数える） |
| 検索 | 根拠の項目が上位3件に入る | `src/lib/ai/faq/search.test.ts`（Claude を呼ばないので CI で毎回流す） |
| 載っていないこと | 推測で答えない | 評価データの「載っていないこと」 |
| 応答時間・料金 | 中央値 10秒以内・1回 5円以内 | 記録した応答時間・トークン数 |

## 4. 設計の判断

| 判断 | 理由 |
|---|---|
| 検索は文字の2-gram の BM25（外部の検索サービス・埋め込みを使わない） | 文書が少ない（20数項目）。依存とキーを増やさず、検索の正しさをテストで毎回確かめられる。文書が増えたら埋め込みを検討する |
| 文書を全部プロンプトに入れず、検索して渡す（RAG） | 文書が増えても1回の料金が増えにくい。引用の単位（項目）がはっきりする |
| 引用は Claude の citations（search_result ブロック）を使う | 引用の場所（どの項目のどの文か）は API が返すので、AI が出典を作れない。サーバーは、ルールにある項目への引用だけを画面に出す |
| 構造化出力を使わない | citations と同時には使えない（API の制約）。答えは文と引用のまま画面に出す |
| 値は API から | 文書に書くと、料金を変えたときに古い値で答える |

## 5. リスクと対策

| リスク | 対策 |
|---|---|
| もっともらしい作り話 | ルールの検索結果だけを根拠にさせ、引用を付けさせる。引用も API の値もない答えには「ルールにもとづいていません」と画面に出す |
| ルールの文書とコードの食い違い | 文書を変えたら検索用データを作り直す（CI で確かめる）。ルールを変える PR で文書も直す（`docs/rules/README.md`） |
| 操作を頼まれる | 道具は読み取りだけ。手順をルールにもとづいて案内する |
| 入力に指示を紛れ込ませる | 評価データに入れる。道具は読み取りだけで、他の会員の情報を返すものはない |
