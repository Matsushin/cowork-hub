# 課題メモ：売上・利用状況を質問できる分析アシスタント

作る前に、だれが・何に・どれくらい困っているかと、成功の基準を決める。
**【要確認】** の印は、運営者（松田）の実際の経験で確かめて書き直すところ。

## 1. 使う人

| 人 | 状況 | 今のやり方 |
|---|---|---|
| 運営者（経営・拠点の担当） | 月初に先月の数字を振り返る。どの拠点・曜日・時間帯が伸びたか、どこが空いているかを知りたい | 管理画面の「売上」で月ごとの拠点別の表を見る。曜日・時間帯・稼働率は見られないので、予約一覧を書き出して表計算で集計する **【要確認】** |
| 拠点のスタッフ | 「会議室を増やすべきか」「平日の朝のキャンペーンをやるか」を決める材料がほしい | 運営者に聞く・感覚で決める |

## 2. 困りごと（仮説）

1. **見たい切り口が画面にない**：今の画面は「月 × 拠点」の売上だけ。曜日・時間帯・会議室の稼働率・会員の増え方は、データを書き出して自分で集計するしかない
2. **質問が毎回少しずつ違う**：「先月と比べて」「渋谷だけ」「平日の午後だけ」など、問いごとに画面を作るのは割に合わない
3. **数字の取り違えが怖い**：手で集計すると、期間（月末の締め）や、取り消した予約を含めるかなどの数え方がぶれる

## 3. 作るもの（範囲）

- 管理者が自然な文で質問すると、AI が**集計用の API（道具）だけ**を呼んで数字を集め、短い答えと「主な数字」を返す
- **AI に SQL は書かせない**。集計は Rails の決まった処理（`GET /api/admin/stats/usage`・`/stats/members`・`/sales`）で行い、数え方（取り消しを除く・締め忘れを閉店時刻で締める・稼働率の分母）はコードで一つに決める
- **AI に計算をさせない**。答えに出す数字は、道具が返した値（と、その差・比）だけ。サーバーが**数字を道具の結果と照らし合わせ**、照らし合わせられない数字には印を付けて出す
- 期間や拠点が分からないときは聞き返す。分からない月（データがない）は「データがない」と答える

範囲外：数字の書き出し（CSV）・グラフ、会員個人の情報（名前・メールアドレス）、データの変更、予測

## 4. 成功の基準

| 指標 | 目標 | 測り方 |
|---|---|---|
| 答えの正しさ | 評価データで 90% 以上 | `frontend/evals/analytics/cases.json` を流し、答えに入るべき拠点名・数字を、同じ API を直接呼んだ値（正解）と照らし合わせる |
| 確かめられない数字 | 0件 | 答えの数字のうち、道具の結果と照らし合わせられなかったものを数える |
| 安全 | 個人の情報を答えた件数 0、会員がこの機能を使えた件数 0 | 評価データの安全のケース、権限のテスト（会員は 403） |
| 応答時間 | 中央値 20秒以内 | 記録した応答時間（集計を何回か呼ぶので、予約アシスタントより長くてよい） |
| 料金 | 1回の質問あたり 15円以内 | 記録したトークン数から計算 |
| 振り返りの手間 | 書き出し → 表計算（**【要確認】** 1回 30分ほど？）→ 質問1回 | 運営者に聞く |

## 5. リスクと対策

| リスク | 対策 |
|---|---|
| AI がもっともらしい数字を作る（ハルシネーション） | 答えの数字をサーバーが道具の結果と照らし合わせる。照らし合わせられない数字は画面で印を付け、評価で数える |
| 数え方のぶれ（取り消し・締め忘れ・月の境目） | 集計は API の決まった処理だけ。AI は期間とまとめ方を選ぶだけ |
| 個人の情報が出る | 道具は人数・件数・金額だけを返す集計の API に限る（会員一覧の API は渡さない）。評価データにケースを入れる |
| 会員が使う | 画面は管理画面の中だけ。Rails でも、利用記録（analytics）を始められるのは管理者だけ。道具の API も管理者だけ（Pundit） |
| 入力に指示を紛れ込ませる | 道具は読み取りだけ。データを変える操作はない |
| 料金の使いすぎ | 1日の回数の上限（予約アシスタントと同じ仕組み）、Console の月の上限額 |
